# iOS 伙伴页录音中断改造与验收

基线为 `feat-2026.11.24` 的 `34ce7d2f9`，上一版改造提交为 `5def38bc5`。每轮记录源码指纹、IPA SHA-256、设备、iOS 和对端 App 版本。使用开发签名测试包和测试环境。包版本号相同的产物也要单独记录指纹。

## 目标与改动对照

飞书和微信来电或接通后，女娲暂停采集、计数和波形。暂停持续到挂断，覆盖女娲原本在前台和原本在后台的情况。挂断时在后台开始真实采样，稍后打开面板时按实际录音时长接着显示。完成后，接通前和挂断后的有效音频按时间顺序封口、上传并转写。用户手动暂停只接受手动继续。系统电话的接通暂停和挂断续录作为回归用例。

| 环节 | 11.24 基线 | 上一版 `5def38bc5` | 本次实现与验收 |
| --- | --- | --- | --- |

| 后台续录 | 收到 `.ended` 时尝试后台开新段，缺少回调时等回前台 | 同一默认入口，增加录音器计时检查。iOS 27 恢复建议默认仅观测 | 新旧系统信号汇入同一个原生恢复流程。真机证实挂断后能在后台采样的组合通过验收；无信号的组合保留暂停，列为后台目标未通过 |

## 上一版的实现

1. **中断时先保全音频。** 仍由 Swift 在确认麦克风被占用后封口，原生把每次打开和封口的文件登记到会话目录。UTS 确认分段状态已经写入本地缓存后清除恢复索引。冷启动时读取剩余索引，补入 UTS 尚未登记的文件。时长优先使用文件音轨，读数为零或暂时无法解码时保留非空文件。上传队列先做有限次数的补封口，并复核音频能否读取。
2. **首段上传独立于续录。** 在首段开录且已有笔记 ID 时，把该文件的上传参数交给原生。确认中断并封口后，测试宿主可直接把该文件提交给后台 `URLSession`。UTS 对同一路径读取原生任务状态和业务回执，成功后才标记已上传。未能交接给系统、业务失败或任务被取消时，原上传队列按段号补传。当前只为段号 0 接入原生传输。
3. **收到恢复信号后另开新段。** 继续支持旧 `ended` 和系统电话路径。原生检测到新录音器已开始计时后才把新段交给 UTS，同属一条笔记。iOS 27 恢复建议默认只记录送达时机，启用实验开关后才触发恢复。混音有单独开关，便于区分「通知到达」和「音频会话能重新激活」。收不到信号的后台场景保持暂停，回女娲后走现有兜底。面板分别显示通话暂停与首段上传状态。

## 本次实现与验收顺序

1. **先收紧原生状态和面板联动。** Swift 管理录音中、通话暂停、恢复待确认、手动暂停及完成。接通相关中断确认录音器停写后，使用最后确认的采样时长冻结界面并封口。响铃导致短暂中断时，先验证原录音器和系统信号，再决定同段继续或进入通话暂停。路由变化、回页、其他 App 无声都只用于诊断或已获许可的重试，不能把通话暂停推进到恢复。收到系统恢复信号后才激活会话并开候选段，等采集时间推进，再向 UTS 发布已恢复。`restart`、实时路径和音量入口统一遵循确认状态。取消恢复时作废该代次的定时任务和回调。
2. **修复文件保全和顺序。** 在原生登记分段时保存稳定的顺序标识。结束或重启对账时，按登记顺序补齐尚未入队的段，再处理仅在停止回调里出现的路径。用路径去重，保留已上传段号。验证容器、音轨和可读样本。确认无音频数据的候选段不参与上传和完成。含音频但尚不可读的文件保留并尝试修复，失败时明确标记待修复，已验证有效段可以继续上传。服务端收到全部有效段且无待修复音频后发起完整转写。
3. **验证后台是否会收到足以恢复的信号。** 旧系统记录 `.ended` 的到达时刻。iOS 27 使用支持该 API 的 Swift 和 SDK，在同一测试包先观测恢复建议，再单独开启恢复开关。区分响铃结束与接通后的中断结束，结合本轮暂停时间线和系统仍报告的音频占用过滤信号。将通知送达、会话激活和首个有效采样分别记时，区分没收到信号、开麦失败和开麦后未写入。仅在信号可用且采集得到确认时续录，同一轮恢复只开一个有效段。无信号或进程被挂起时保全已录分段，回到女娲保持暂停，由用户在挂断后点继续。这一轮标记为后台目标未通过。混音现有开关只做对照，单独测试通话静音时会不会误续录。
4. **按实际通过的组合启用。** 飞书、微信各自验证前台、后台和长通话。按 App、iOS 版本和场景记录结果，两端应用分别通过后才宣告对应场景达标。首段后台传输检查单独保留，服务端收到首段时继续检查挂断后的音频和最终转写。

旧音频中断的开始事件可能没有对应的结束事件。iOS 27 新增独立的恢复建议，实际后台送达和录音恢复由真机确定。 [Apple 旧中断机制](https://developer.apple.com/library/archive/documentation/Audio/Conceptual/AudioSessionProgrammingGuide/HandlingAudioInterruptions/HandlingAudioInterruptions.html) · [Apple 音频生命周期通知](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions)

## 设备和账号

- Mac 飞书客户端登录账号 A，作为主叫。待测 iPhone 飞书客户端登录不同的账号 B，作为被叫。测试只在这两个已确认的账号之间拨打。若两台 iPhone 用同一账号 B，轮测时隔离另一台的通知，避免接错。
- 微信语音使用同样的双账号和放音流程，结果与飞书独立记录。
- 按设备实际系统版本选择一台覆盖 iOS 27，一台覆盖旧通知。开始时用手机内置麦克风，断开蓝牙耳机。接通后静音 Mac 的通话麦克风。标识音从 Mac 扬声器播放，由 iPhone 麦克风在现场拾取。
- 人只需要登录账号。拨号、接听、挂断和切页由操作者负责，所有待采集声音由脚本播放。长通话过程中保持静音即可，测试者无需持续说话。

## 四个可识别的标识音

在 worktree 根目录生成。每个 WAV 约 4 秒，由不同的双音组成。脚本使用 macOS 默认音频输出，执行前将输出指向 Mac 扬声器。

```sh
python3 scripts/ios-tester/voice-note-qa.py generate
python3 scripts/ios-tester/voice-note-qa.py play before
```

| 标识 | 播放时机 | 要证明的结果 |
| --- | --- | --- |
| `before` | 伙伴页开始录音后，接听前 | 第一段保留了真实采样 |
| `during` | 两端都显示已接通后 | 女娲录音中没有通话期间的采样 |
| `after` | 确认挂断后立刻播放，iPhone 留在飞书 | 后台续录是否真正开始 |
| `returned` | 打开女娲之后播放 | 回前台的兜底路径是否可用 |

所有播放命令把开始和结束时刻写入 `out/ios-voice-note-qa/playback.jsonl`。每轮用 `--out out/ios-voice-note-qa/<case>` 保留自己的时间线。语音通话起止时间由操作者记入同一轮记录。

## 真机操作和判定

1. iPhone 打开女娲伙伴页录音，等面板开始计时，播放 `before`。拨号时分别让女娲停在前台和已在后台。确认接通后播放 `during`，再安排一段双方静音。增加一轮在对方仍通话时返回女娲，核对计时和波形持续暂停，再切走。短通话维持约 15 秒，长通话维持至少 3 分钟。
2. 通话期间在另一客户端或测试环境服务端查看笔记的第一段。分别记下原生封口、后台任务提交、服务端落段的时刻。挂断后仍从另一客户端查看一次。只有服务端返回第一段并且该段可播放，才记为后台已入库。
3. 从 Mac 挂断。iPhone 继续留在对端 App，立刻播放一次 `after`，停留至少 20 秒，再回女娲播放 `returned`，最后点完成。记录挂断、原生首个有效采样和回女娲的时间，先对齐 Mac 与 iPhone 时钟。挂断到首个采样暂以 2 秒为工程观察线，同时保留实际延迟，后续按真机结果确认验收口径。用日志中的 `firstSampleEstimateEpochMs` 辅助定位首个采样时刻，实际采到的内容以标识音为准。录音需包含挂断后、回女娲前的 `after`。检查面板返前台显示已录，计时包含后台实际续录时长并排除通话时长，波形保留暂停前的位置并从有效采样继续。单独诊断恢复偏迟时可以重复播放 `after`。
4. 用 `[voice-note] m4a writing localId=...` 确定本轮录音目录。在测试包允许访问容器时复制该目录，或导出测试音频。最终完成后 App 可能清掉已上传的本地文件，介质可提前复制或从服务端下载。VAYS 对照通过分享功能导出测试录音，按播放时间轴人工确认，或按通话边界切段后交给检测器。

```sh
python3 scripts/ios-tester/voice-note-qa.py --out out/ios-voice-note-qa/feishu-long play during
python3 scripts/ios-tester/voice-note-qa.py --out out/ios-voice-note-qa/feishu-long play after --repeat 1

xcrun devicectl device copy from --device "$IOS_QA_DEVICE" \
  --domain-type appDataContainer --domain-identifier com.nuwax.app \
  --source "Documents/voice-notes/$VOICE_NOTE_QA_LOCAL_ID" \
  --destination out/ios-voice-note-qa/feishu-long/segments

python3 scripts/ios-tester/voice-note-qa.py check --expect background /path/to/first.m4a /path/to/next.m4a
```

按服务端分段顺序下载文件并传给检测器，逐段验证可播放。连续中断时，用 Mac 预先合成三条可区分的短句，在首次接通前、第一次挂断后和第二次挂断后分别播放，核对转写中的顺序。标识音用于自动判断采集时窗。兜底场景用 `--expect foreground`，要求 `after` 缺席、手动继续后才出现 `returned`，结果仍计为后台目标未通过。手动暂停或结束场景用 `--expect no-resume`。脚本判断音频内容，延迟、界面、分段顺序和服务端转写分别核对。

## 对照组与发布门槛

| 组别 | 设置 | 通过标准 |
| --- | --- | --- |
| 基线、当前和下一版 | 锁定三个包，飞书和微信各跑接听前在前台、后台及短、长通话 | 每轮保留原生日志、标识音和服务端结果，逐项记录暂停、采样延迟和分段交付 |
| 首段保全 | 默认路径，连续中断、失败候选段、强退后重启 | 找回未登记的有效段，顺序正确，可播放。确认空段不会挡住提交，真实待修复音频有可见状态 |
| 原生后台上传 | 只启用测试宿主的后台上传 | 留在飞书时服务端有第一段。断网、鉴权失败或强退后保留文件，重进女娲按原段号补传。服务端同一笔记只有一条首段 |
| iOS 27 恢复通知 | 先仅观察新旧通知。再启用新通知的恢复路径，混音关闭 | 新通知在挂断后、回前台前送达。激活成功，新段出现 `after`，通话期间无 `during` |
| 混音 | 只启用混音，保持 iOS 27 恢复开关关闭 | 对比旧通知送达和音频会话激活结果。不能在对方仍通话时误启录音 |
| 回归 | 拒接、普通切后台、来电前手动暂停、恢复待确认时手动暂停、通话中回女娲、通话中点完成、蜂窝或 FaceTime、重复来电、低网速 | 拒接后原录音按系统信号继续，通话中返回面板仍停。手动暂停和完成后旧事件不会复活录音，系统电话继续在挂断后恢复 |

本次实现的两个续录开关默认关闭。真机先逐项验证新通知和混音。无恢复信号场景需要独立记录，按安全兜底交付时明确标记后台目标未通过。

后台上传实验由独立测试宿主提供 `AppDelegate` 回调，打包时设置 `NUWAX_VOICE_NOTE_BACKGROUND_UPLOAD=1`。提交同一条笔记第 0 段，且要求笔记 ID、鉴权和源文件路径已在中断前交接。其他分段、未交接和失败通过既有补传队列处理。普通基座或云包需接入并验证同一宿主回调才能启用。

iOS 27 恢复和混音从打包后的 App 启动参数读取，每次只传一个。基线验证时不要附加调试器。

```sh
xcrun devicectl device process launch --device "$IOS_QA_DEVICE" --terminate-existing \
  com.nuwax.app -- -NuwaxVoiceNoteResumeRecommendation YES
xcrun devicectl device process launch --device "$IOS_QA_DEVICE" --terminate-existing \
  com.nuwax.app -- -NuwaxVoiceNoteMixWithOthers YES
```

记录 `began`、文件长度、录音时长、后台任务过期、上传响应、新旧恢复通知、音频会话激活错误域及错误码、挂断后的首个可验证采样。出现异常时以音频、日志和服务端读回三者为准。
