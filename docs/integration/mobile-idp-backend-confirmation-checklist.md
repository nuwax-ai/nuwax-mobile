# 移动端联合登录后端确认清单

更新日期：2026-10-13。范围：CAS、微信、飞书的移动 H5 与原生 App 登录、首次关联及账号绑定。

**当前只做文档梳理和方案确认，暂停代码实施。** 请后端同学按问题编号回复已有能力、接口或需要补充的内容，先确定复用方案，再评估开发工作量。本文中的建议不代表已确定的接口合同，也不代表后端尚未实现。

PC 已有统一配置、网页授权、首次注册/绑定和身份管理。移动端主要需要确认：**如何选择合适的授权方式、如何取得可用于 App 业务的登录态，以及如何让所有成功和失败分支返回正确客户端。**

此前的移动前端草稿、测试和文档按用户要求保存到专用分支 `feat/nuwa-zhuoda-2026.10-idp-login`，新增实施仍暂停，未部署；这些草稿不作为接口已确认或功能已上线的依据。详细背景、接口索引和历史验证记录见[评估与实施方案](cas-mobile-assessment-and-plan.md)。

## 优先确认的六个结论

第一次沟通建议先答复以下六项；其余问题可随对应接口文档一起补充。

| 决策 | 需要后端给出的结论 | 详细问题 |
| --- | --- | --- |
| 微信和飞书原生登录 | SDK 返回授权码后调用哪个平台接口；已绑定、自动关联、待手动关联分别返回什么 | A01、B01 |
| CAS 回到原生 App | 复用现有 OAuth2 公共客户端和 PKCE，还是使用已有或新增的一次性会话交接能力 | A02、A03 |
| 公开登录能力 | App 如何识别提供方、支持的平台和授权方式，如何取得公开 AppID；继续复用 PC 配置 | A04、E01、E02 |
| 平台账号一致性 | PC 与 App 如何对应同一个平台用户；哪些情况允许自动关联，哪些必须人工确认 | B02、B03、B04 |
| 移动返回上下文 | 失败、取消、首次注册/绑定、普通登录续接如何返回 H5 或 App，而非 PC 登录页 | D01、D02、C03 |
| 业务会话兼容性 | 获得的 Token 能否用于现有用户、业务、IM 接口；过期、刷新和退出如何处理 | C01、C02、B05 |

## 已知能力和确认边界

依据为 2026-10-13 已核对的文档、接口声明及 PC 页面。这里列出已知能力，后端只需补充移动适用条件或纠正文档差异。

| 已知事项 | 当前依据 | 移动端仍需确认 |
| --- | --- | --- |
| 统一管理入口已经存在 | [PC 登录方式管理](https://testagent.xspaceagi.com/system/config/auth-method) 可配置 CAS、微信、飞书等 | 原生应用配置能否纳入同一 provider，以及公开能力如何下发 |
| 公开登录方式列表存在 | `GET /api/auth/idp/list` 返回 `items`、`autoRedirectIdpId`；item 有 `id/type/name/icon/wechatMode` | 当前公开字段没有原生授权方式、飞书细分标识或 SDK AppID 合同 |
| 网页授权和回调存在 | `GET /api/auth/idp/authorize`、`GET /api/auth/idp/callback`，以浏览器跳转完成流程 | 不能仅据 302 回调就确认原生 SDK code 换平台 Token 已支持 |
| 手机浏览器微信唤起已有文档说明 | [三方登录专项文档](https://testagent.xspaceagi.com/repo/doc/DCmphdX8GiJPzGze) 描述手机浏览器唤起、成功写 Cookie 后返回网页 | 网页唤起微信与返回 Nuwax 原生 App 是不同交接场景，尚未做手机实测 |
| 首次注册和绑定规则已有接口 | `/auth/bind-or-register` 与 `/api/auth/idp/pending/info`、`register`、`bind` | 原生 App 如何贯穿 pending 状态并取得最终业务会话 |
| 部分接口已有 Token 返回 | `pending/register` 声明返回 `LoginResDto`，含 `token/expireDate/resetPass/redirect` | 不能笼统说三方接口都不返回 Token；需要覆盖其他成功分支及安全交接 |
| 身份列表、绑定、解绑存在 | `/api/user/identity/list`、`bind/{providerId}`、`unbind/{identityId}` | App Bearer 适用性、绑定发起账号固定、原生绑定结果返回 |
| OAuth2 授权码与 PKCE 已有声明 | [最新 OpenAPI](https://test-nvwa-api.xspaceagi.com/v3/api-docs) 包含 `/api/oauth2/authorize`、`token` 和 PKCE 参数 | 官方 App 公共客户端、免 client_secret、业务 Token 和 IM 兼容性仍未确认 |

业务成功码为 `0000`。CAS service ticket、微信/飞书授权 code、平台 Cookie、pending token、平台一次性交换码和 App 业务 Token 的用途不同，不能混用。`/api/connector/oauth/exchange` 用于连接外部服务，不作为已确认的平台用户登录接口。

## 后端接口和业务规则

下列问题初始状态均为**待确认**。A 至 D 组应在对应功能开发前明确；已有实现可直接给文档章节、部署环境和脱敏示例，无需重复设计新接口。

### A 授权入口和能力选择

| 编号 | 需要确认的问题 | 期望提供的答复 |
| --- | --- | --- |
| A01 | 微信和飞书分别收到 SDK 授权 code 后，平台是否已有原生登录完成接口？接受何种 code，如何校验对应应用及 state？登录和绑定是否使用不同模式？ | 两个提供方各自的实际方法/路径、鉴权方式、参数位置、必填字段、成功/待关联/失败示例；未支持则说明最小扩展点 |
| A02 | CAS 浏览器授权到 App 的交接是否可复用 `/api/oauth2/authorize` + `/api/oauth2/token`？是否允许官方 App 作为不持有 client_secret 的公共客户端，强制 PKCE S256？未登录及 pending 分支能否完成后继续原授权请求？ | 可复用/部分可复用/不可复用的结论；客户端登记方式、允许的 scope、回调类型、PKCE 校验规则和完整请求示例 |
| A03 | 若 A02 不能直接得到 App 业务会话，是否已有一次性码兑换或其他安全交接接口？补充能力是复用旧模块还是新增？ | 最终选定的链路；发起、完成/兑换、取消或过期的接口合同；不要默认照建评估文档中的四个提案接口 |
| A04 | App 如何根据公开列表识别 CAS、飞书、微信，区分浏览器授权与原生 SDK？同一个 provider 对 Android、iOS、H5 的支持如何表达？自动项在当前端不支持时如何处理？ | 公开能力字段和示例、字段缺失的兼容语义、平台级开关及自动跳转规则；不得通过按钮名称猜 SDK，也不从管理接口读取 Secret |
| A05 | 同一租户多个微信/飞书应用、provider 停用或配置变更时，已发起的移动授权是否仍有效？配置 ID、应用 ID 和租户之间如何约束？ | provider 选择和唯一性规则、在途事务的处置方式、失效错误码；确认不会将旧授权结果关联到新配置 |

### B 首次关联和账号管理

| 编号 | 需要确认的问题 | 期望提供的答复 |
| --- | --- | --- |
| B01 | 已绑定身份、自动关联已有账号、自动注册新账号、手动注册、手动绑定分别如何完成 App 登录？需要人工操作时留在后端网页还是返回原生页面？ | 五个分支的状态/响应及最终会话交付方式；pending 的查询、完成、失效规则；确认普通登录及设置密码后如何继续原事务 |
| B02 | `autoRegisterBind` 已有规则在 App 是否完全复用？手机号与邮箱指向不同账号、缺少属性、邮箱/手机号未经验证、注册关闭或账号禁用时，最终如何判定？ | 现行匹配优先级、可信属性要求和冲突结果；哪些情况必须人工确认，避免移动端自行合并账号 |
| B03 | PC 网站、公众号与微信移动应用如何归一为同一平台用户？飞书不同应用、企业/租户下的身份如何对应？ | 实际使用的身份键及命名空间、UnionID 等标识的适用条件、旧绑定迁移/关联策略；条件不足时的人工关联流程 |
| B04 | 已登录 App 发起绑定后，浏览器若残留另一平台账号，绑定以哪个账号为准？如何防止绑定冲突、重复提交或退出/换号后继续绑定？ | 服务端固定发起账号的方式、是否要求重新认证、冲突错误码、绑定成功响应；绑定操作不应静默替换 App 当前登录账号 |
| B05 | `/api/user/identity/list`、`unbind/{identityId}` 是否接受 App 现有 Bearer？唯一登录方式且未设密码的限制，原生端能否得到明确错误码和可执行的设置密码流程？ | 鉴权兼容结论、解绑业务错误码、设置密码前置认证要求；路径 ID 仍是身份记录 ID，不是 provider ID |
| B06 | 外部身份或平台账号被禁用、移出租户、撤销授权后，已签发的 App 会话何时失效？普通退出是否继续仅退出平台？是否另有 CAS 单点注销要求？ | 现行会话撤销规则、影响范围及检测时点；如要求 SLO，单列需求，不能由“支持 CAS 登录”推定 |

### C 业务 Token 和授权生命周期

| 编号 | 需要确认的问题 | 期望提供的答复 |
| --- | --- | --- |
| C01 | 兑换结果是现有 App 业务 Token，还是 OAuth2 的开放接口 Token？是否能调用 `/api/user/getLoginInfo`、实际业务 API、身份管理与 IM 鉴权？ | 响应字段、token_type/受众/scope、业务和 IM 接受方式；若需二次交换，给出接口和权限边界，不能只用 userinfo 成功证明全部兼容 |
| C02 | Token 有效期、刷新方式、刷新失败、同账号多端登录和退出撤销如何处理？`expireDate/resetPass` 的类型及语义是否与普通登录一致？ | 生命周期合同及示例；是否有 refresh_token、轮换/吊销策略；退出影响本设备还是所有设备、是否同步撤销刷新凭证 |
| C03 | state 与平台事务由谁创建、保存、验证？如何绑定业务域/租户、provider、客户端、登录或绑定模式及回调地址？ | 实际字段及校验职责，SDK code 与平台交换 code 的区分；SDK 自身协议与平台交接的 PKCE 分开说明 |
| C04 | 授权事务、启动票据、pending、SDK code 和平台交换 code 的有效期分别是多少？重复兑换、重复回调、兑换成功但响应丢失时如何处理？ | 有效期、原子消费和防重放规则、可重试错误码、幂等取回或重新发起方案；评估文档中的寿命数字仅为讨论值 |
| C05 | 用户取消、授权超时、切企业域、退出、开始另一笔登录或进程重启后，旧事务如何失效或恢复？ | 服务端取消能力及凭证要求、超时处理、并发事务规则、恢复所需最小信息；迟到回调不能重新登录或绑到新账号 |

## 回复格式和接口材料

建议每项使用同一格式；不适用或本期不纳入也明确记录原因。已有文档覆盖时只需附精确章节和适用版本。

```text
问题编号：A01
结论：已支持 / 需扩展 / 未支持 / 不适用 / 本期不纳入
实际行为或选定方案：
接口或文档：方法、路径、文档章节、适用环境与版本
请求：鉴权方式、Content-Type、参数位置、字段类型/必填/可空
响应：成功、待关联、失败的脱敏示例；HTTP 状态及业务码
约束：有效期、重试/幂等、租户和账号归属（按本项需要填写）
责任方与预计确认/可联调时间：
```

接口材料至少覆盖：原生 SDK 发起/完成、CAS 到 App 会话交接、pending 注册/绑定、绑定完成、取消/过期、刷新/退出（实际方案没有独立接口时说明相应行为）。公开字段可直接填文档；AppSecret、client_secret、私钥、真实 Token、授权码和密码不填入清单。

后端回复后先更新本清单的结论、接口对照和方案取舍。**现有草稿提交保存不代表恢复代码开发、联调或发布；恢复实施另按用户后续指令执行。**
