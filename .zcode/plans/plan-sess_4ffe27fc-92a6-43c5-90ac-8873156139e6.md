## 修复目标
解决"流式输出时看不到 loading 和逐字效果"——根因是大量历史消息(尤其 mixed 重内容)的全量 markdown 解析在挂载时(immediate watch)串行霸占主线程,饿死 loading 动画帧和流式合并窗。

## 改动一:Mock 测试场景——seed 历史与流式串行
**文件**: `subpackages/pages/chat-conversation-component/chat-conversation-component.uvue`(初始化处 ~3567-3573)

当前 `seedMockHistoryIfNeeded()` 和 `runMockPerfStream()` 几乎同时调用,历史全量解析和流式抢主线程。改为:seed 历史后延迟启动流式(等历史首屏解析渲染完,用 nextTick + setTimeout 错峰)。

```
if (isStreamPerfMockEnabled()) {
  isPerfMock.value = true;
  service.seedMockHistoryIfNeeded();
  startPerfFrameProbe();
  startVsxDebugProbe();
  // 等 seed 历史的首屏全量解析落定再启动流式,避免两者抢主线程
  // 历史越多等越久(粗略按 history 估算),最少 500ms
  nextTick(() => {
    const cfg = getStreamPerfConfig();
    const delay = Math.max(500, cfg.history * 30); // 100条≈3s
    setTimeout(() => service.runMockPerfStream(), delay);
  });
  return;
}
```
> 需 import getStreamPerfConfig(已在 mockStreamPerf.uts 导出)。

## 改动二:渲染层根治——历史消息延迟分批解析
**文件**: `subpackages/components/ai-msg/ai-msg.uvue`(`scheduleBodyMarkdownParse` ~902-948)

当前非流式历史消息(`streaming==false`)在 watch `{ immediate: true }` 触发时,立刻 `runBodyMarkdownParseNow(true)` 全量解析。100 条历史同时挂载 = 100 次全量解析瞬间打满主线程。

改为:非流式历史消息的首次解析用 `requestAnimationFrame` + 随机微延迟错峰,让浏览器/主线程在解析间隙能渲染 loading 动画帧和流式 chunk。具体:
- 在 `scheduleBodyMarkdownParse` 的 `streaming==false && 非末条历史` 分支,把 `runBodyMarkdownParseNow(true)` 包进 `requestAnimationFrame`(让出当前帧)
- 用一个全局递增计数器给每条消息加 0~N ms 的 `setTimeout` 偏移,使 100 条历史的解析分散到多帧而非同一帧

```
// 非流式历史:错峰延迟解析,避免首屏 N 条历史同时全量解析打满主线程
if (streaming == false && isLastMsg.value != true) {
  scheduleHistoryParseDeferred();
  return;
}
```
新增 `scheduleHistoryParseDeferred()`:
- 模块级计数器 `historyParseSeq`,每条递增
- `delay = (historyParseSeq % 8) * 16ms`(8 条一帧错峰,每帧 ~16ms)
- `requestAnimationFrame(() => setTimeout(() => runBodyMarkdownParseNow(true), delay))`

**安全性**:
- 延迟期间 `renderMarkdownElList` 为空 → markdown 区域暂空白(比全屏卡死好),loading 圆环正常转
- `forceDone=true` 语义不变,只是延后执行
- 流式末条(`isLastMsg=true`)不受影响,仍走原有 immediate 路径
