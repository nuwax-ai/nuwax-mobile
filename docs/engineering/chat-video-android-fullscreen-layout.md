# Android 会话视频退出全屏后画面偏移

## 2026-11-20 真机排查

设备：华为 ELS-AN00；应用：`com.nuwax.app`，1.4.0 调试包。
在测试群的视频消息上复现：进入全屏，再返回会话，视频卡左侧大片黑色，右侧仅显示部分画面。

这条消息的「缩略图」实际是常驻 `<video>` 的暂停帧。通过 adb 读取原生视图树：

| 层级 | 异常时尺寸（物理像素） | 恢复后尺寸（物理像素） |
| --- | --- | --- |
| 行内卡片 / 自绘控制条 | 663 × 497 | 663 × 497 |
| video 根节点 | 1200 × 497 | 663 × 497 |
| 内部容器 / VideoImpl | 1200 × 497 | 663 × 497 |

1200 是该设备屏宽。退出全屏后，video 根节点残留的内联 `width` 为
`362.26416px`（逻辑像素），覆盖原来 class 中的 200px 行内宽度。
竖视频仍在屏宽内居中，外层卡片又启用了 `overflow: hidden`，因此只露出右侧部分画面。

## 探针验证

通过 Android JDWP 调试接口，在主线程上对现有播放器做临时样式探针，没有重新打包应用：

1. 只恢复内部容器宽度后，同一播放器第 5 秒的暂停帧立即恢复居中。
2. 内部容器恢复框架默认 `100%`，仅写回 video 根节点宽度，同样恢复；
   `VideoImpl` 原生实例保持不变，未调用 seek、play、pause 或重新加载 src。
3. 再次进入全屏并返回，屏宽残留重新出现，可重复复现。
4. 使用最终修复的公开 API 组合：读取父容器和 video 的 `getBoundingClientRect().width`，
   分别得到约 200.15094 与 362.26416，再通过 `style.setProperty("width", ...)`
   写回父容器宽度。原生视图树恢复为 663 × 497，画面恢复居中。

证据支持当前设备/调试包上的全屏退出布局恢复问题；没有仅凭本地离线 SDK
版本推断手机框架版本，也没有据此认定所有 Android 机型均受影响。

## 最终应用侧方案：绘制前拦截返回的错误帧

300ms 恢复宽度、下一渲染帧恢复宽度两版均经用户回归：尺寸最终正确，但横/竖视频
仍会先偏右再移回中央。因此已移除这两版返回布局补偿，不再靠全屏退出事件后的延时
修正可见画面。原有 300ms 计时器只保留原先「进入全屏补调播放」的职责。

新增 `utils/androidChatVideoLayout.uts`，仅 Android 编译；会话控制条在调用
`requestFullScreen` **之前**捕获原位原生父容器并安装 `ViewTreeObserver.OnPreDrawListener`：

1. `video.getAndroidView()` 在本机实际返回内部 `TextureView`，不是框架搬动的外层。
   沿 Android 原生父链定位原位容器的直接子视图，观察它「移出 → 移回」的过程。
2. 全屏播放时正常放行，不调整全屏尺寸；也不改变播放、暂停或进度。
3. 容器搬回时，如果外层或视频纹理仍保留全屏尺寸，恢复原位宽高并从 `onPreDraw`
   返回 false，阻止该错误中间帧提交。只有外层和纹理的宽高都一致、布局请求已完成，
   才解除监听并放行会话返回帧。
4. 控制条销毁、页面隐藏/卸载、请求失败及重新发起全屏都会清理旧监听；未真正进入
   全屏的守卫 1.5s 后释放。返回阶段至多拦截 250ms，避免异常布局卡住整页。
5. 只处理 `chatVideoPlayer-` 消息视频，不修改合并转发详情等其他播放入口。

## 该方案的真机探针与检查

在原有调试包内加载可移除的 Java/Dex 临时探针，使用与上述方案相同的原生观察器、
父链判断、公开元素样式 API 和尺寸检查。没有重新打包 App，没有修改框架私有类或字段。
分别操作当前会话中的横、竖视频进行全屏往返，返回后的两张卡片均居中。

探针读取到的返回绘制过程（18:54:52）：

```text
block=1 root=1200x497 target=662x497 texture=1200x497
ready blocked=1 elapsed=25 size=662x497
```

竖视频探针同样读到 `movedOut=true, blocked=1, stopped=true`。
这些证据确认错误尺寸的绘制请求被拒绝，正确尺寸时才放行；截图仅说明最终画面，
不单独用静态截图声称动画已验收。探针已移除，临时 Dex 文件和调试转发已清理。

29 项相关逻辑测试通过，覆盖进入全屏前安装守卫、横/竖尺寸适配、外层和纹理分步布局、
正确布局不拦截、快速重进、离页/销毁、请求失败和超时放行等路径。
条件编译结果比对确认 iOS、鸿蒙、H5、Web、微信小程序脚本逻辑与修改前一致，
`git diff --check` 通过。

未运行 HBuilderX 或平台编译。当前源码的 UTS 集成仍需下次 Android 热更新后回归，
不能把临时 Java 探针及逻辑测试表述为新构建已验收。

## 进入全屏时的框架异常

用户提供的 18:33:45 日志为 `ConcurrentModificationException`，堆栈从
`LinkedHashMap$LinkedKeyIterator.next` 进入 `UniElementImpl.updateStyle$lambda$8`，
由框架的 `onLayoutChange` / Android `View.layout` 触发。该次退出宽度修复日志是
18:34:14，发生在报错之后，不能把这次进入全屏的异常归因于退出时的宽度修复。

同时出现的 `white-space` 警告指向框架内部的 `uni-video-volume-button` view。
这两项均没有指向业务代码的直接堆栈；目前没有证据证明延时或捕获业务层
`requestFullScreen()` 能修复它们。本次不修改框架私有样式、集合或 SDK，也不声称
已解决进入全屏时的异常；保留日志以供后续框架版本回归/问题反馈。
